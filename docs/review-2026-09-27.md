# Project review — 2026-09-27

Reviewed baseline: `1d4eb47`. This is a review and implementation handoff, not a
set of code fixes. Application code, tests, and workflows were left unchanged.
The separate requested documentation change consolidates all three specifications
into `specs/spec.md` and updates their links. Plaintext RPC URLs/history are an
accepted user decision and are not reported as a defect.

## 1. High: interrupted broadcast loses the transaction signature

Locations: `src/commands/send.ts:131–139`, and the equivalent broadcast blocks in
`token-send.ts`, `staking.ts`, and `lending.ts`; `src/solana/rpc.ts:53–64`.

The code gets the signature exclusively from the successful `sendTransaction`
response. If the RPC accepts/forwards the signed transaction but the response is
lost, `rpcRequest` throws a generic broadcast error. The user gets neither the
locally available transaction signature nor an explicit warning that the
transaction might have executed. The careful signature-bearing errors in
`confirmSignature` do not apply because that function has not been called yet.
Retrying the command constructs a different transaction and can pay twice.

Suggested fix: extract the signature from the signed transaction before submitting
it; retain it in every ambiguous broadcast error and tell the user to inspect it
before retrying. Do not automatically rebuild/re-sign an ambiguous submission.

Required regression: a fake RPC accepts the submitted bytes and then drops the
response. Assert a signature-bearing unknown-outcome error, no second signing or
broadcast, and successful inspection of the original signature. Cover all write
families sharing this pattern. This finding was established by source inspection;
no actual network-failure transaction was sent during the review.

## 2. High: the Devnet stake lifecycle cannot resume

Location: `test/e2e/run_devnet_lifecycle.py:89–160`.

`minimum` is assigned only inside `if not chain_accounts`, a branch that returns
after creating a stake account. Every subsequent run with an existing stake
account references `minimum` at line 160 without assigning it, raising
`UnboundLocalError`. Consequently the advertised cross-epoch suite cannot reach
its activating, active, deactivating, or inactive branches. Python syntax checks
and the existing proxy tests cannot catch this runtime path.

An offline reproduction with RPC, Docker, fixture, and proxy calls mocked reached
the existing-account path and raised `UnboundLocalError: cannot access local
variable 'minimum' where it is not associated with a value`.

Suggested fix: obtain the live minimum independently of faucet funding, and
exercise every resumed state with offline orchestration tests. Consider whether
a later protocol minimum increase should prevent cleaning up an older stake.
After the fix, demonstrate an actual complete Devnet lifecycle across epochs;
creation alone does not validate deactivation or withdrawal.

## 3. Medium: faucet failure also prevents funded lifecycle progress

Location: `.github/workflows/devnet-e2e.yml:47–65`.

The lifecycle is a later step in the same job as smoke. Its `if` has no status
override, so a smoke failure skips it. Smoke requires funding fresh wallets,
whereas an existing lifecycle wallet can already have enough fees to deactivate
or withdraw. A public faucet outage/rate limit therefore prevents even an
explicitly requested lifecycle run from advancing or cleaning up existing stake.
The implicit status condition is documented by
[GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions).

Suggested fix: give lifecycle its own job, or explicitly allow it after a smoke
failure while still requiring the build and deterministic gates to succeed.
Validate a failing faucet/smoke case with a funded lifecycle account. Do not
silence smoke failures or submit through an unverified cluster to solve this.

## 4. Medium: closed stake accounts remain as permanent unknown entries

Locations: `src/commands/staking.ts:428–435` and `481–535`.

Creation adds a local stake-registry entry, but a confirmed full withdrawal never
retires it. The next listing appends every registry address missing from the
successful on-chain discovery as `state: "unknown"`. Thus an account just closed
by this CLI remains in `stake list`, completion, and status recovery-hint counts.

Offline reproduction used the real registry writer and `readStakeAccounts`, with
both chain queries returning empty arrays. The result still contained the saved
address with `state: "unknown", source: "local-registry"`.

Suggested fix: retire local entries after confirmed closure and reconcile missing
hints through an authoritative account lookup. Do not discard recovery hints just
because an RPC request fails. Test create, full withdrawal, and list again using
the same config directory; the current lifecycle recreates that directory on each
invocation and cannot catch this persistence bug.

## 5. Medium: confirmation can misclassify an included transaction as expired

Location: `src/commands/send.ts:202–219` (shared by all write commands).

When the requested commitment is `finalized` and status is already `confirmed`,
the code still checks blockhash expiry and throws as soon as the current block
height exceeds `lastValidBlockHeight`. That height limits transaction inclusion;
it does not undo a transaction already included while awaiting stronger
confirmation. The same race can occur if inclusion happens between the status
read and the height read.

Offline reproduction passed a fake RPC returning `confirmed`, a block height of
101, and last-valid height 100; it would return `finalized` on the next status
poll. `confirmSignature` instead threw `ConfirmationError` on the first poll.

Suggested fix: distinguish inclusion, expiry, and finality; recheck status at an
expiry boundary and preserve an unknown outcome where necessary. Test pending to
confirmed to finalized, expiry with no inclusion, and the status/height race.
See the official [Solana confirmation and expiration guide](https://solana.com/developers/cookbook/transactions/confirmation).

## 6. Medium: slow confirmation/passphrase entry sends a stale transaction

Locations: `src/commands/send.ts:56–58,122–139`; the token, stake, and Jupiter
transaction handlers follow the same ordering.

The blockhash is fetched before simulation, the confirmation prompt, and the
passphrase prompt. After an arbitrarily long human pause, the old message is
signed and sent with `skipPreflight: true`, without checking its remaining
lifetime. A user carefully reading the preview or retrieving a passphrase can
therefore approve a transaction that is already expired.

Suggested fix: handle expired/near-expired lifetimes before submission, rebuilding
and simulating as needed while preserving the approved wallet, destination, and
amount. Renew consent if material transaction details change. Test a delayed
confirmation and a delayed passphrase, not just immediate automated input.
Solana's [official guidance](https://solana.com/developers/cookbook/transactions/confirmation)
specifically recommends fresh blockhashes near signing.

## 7. Medium: the launcher pollutes JSON stdout with pull output

Location: `scripts/sol-wallet:25`.

`docker pull` inherits stdout before the CLI starts. Consequently
`scripts/sol-wallet -c status --json` emits Docker pull/status text before the JSON
result. Even an already-current image normally emits pull status. This breaks
JSON consumers and the documented one-result stdout contract through the primary
launcher. Existing Docker tests invoke the image directly and miss the wrapper.

Offline reproduction sourced the unmodified wrapper with a stub Docker command:
stdout contained two pull-status lines followed by the JSON object.

Suggested fix: retain mandatory pull-on-launch, route its progress to stderr, and
test the wrapper's stdout/stderr contract with a stub Docker executable for both
pull success and failure.

## 8. Medium: an unhealthy default prevents status for a healthy selected wallet

Location: `src/commands/wallet-management.ts:301–312`.

After a default wallet's keystore becomes missing/invalid, explicitly selecting a
different healthy wallet allows its balance and other commands to work. However,
`status` unconditionally checks the default's keystore and throws before reading
the selected wallet's balances. The saved preference for the next process should
not hide the current explicitly selected wallet's health and balances.

Suggested fix: preserve selected-wallet and registry integrity checks, but report
an unrelated default's unhealthy state as a separate diagnostic. Test healthy B
selected with A saved as default and A's keystore missing, in both one-shot and
interactive selection paths. This finding is based on source inspection.

## 9. Medium: keystore KDF parameters have no resource bounds

Locations: `src/wallet/keystore.ts:35–41,227–234`.

The schema accepts any positive integer for Argon2 memory, iteration count, and
parallelism. Unlock passes them to the native KDF before the authentication tag
can establish that the metadata is genuine. A corrupted or malicious restored
keystore can therefore request excessive memory/CPU during unlock, migration, or
recovery. This requires placing the file in the wallet store and attempting to
unlock it; it is not a remote RPC-triggered issue.

Suggested fix: reject unreasonable KDF parameters before invoking Argon2, with
documented supported bounds that retain legitimate existing keystores. Test
oversized parameters with a spy asserting that the KDF is never called. No
resource-exhaustion payload was executed in this review.

## 10. High: the lifecycle runner could deactivate unrelated wallet stake

Location: `test/e2e/run_devnet_lifecycle.py` account selection and authority
checks.

The runner originally selected the sole stake account owned by its configured
wallet. Authority equality does not prove that the test created that account;
an active pre-existing account could therefore be deactivated and later
withdrawn by the scheduled test.

Suggested fix: persist a lifecycle identity only after successful test creation,
then resume only the recorded stake-account address. Stop without writing if
stake exists but no saved identity is present. Never persist the private key.

## Fixes and validation

All ten findings have been addressed in the working tree. The lifecycle now
reads the live delegation minimum on every run, records its public test-account
identity in a protected-branch GitHub Actions cache, and refuses to select
unrecorded wallet stake. Its workflow can advance the lifecycle after a smoke
or faucet failure only if source checks, image build, tests, and state restore
passed; it still fails the overall run for a smoke failure. Cache actions use
the Node 24 compatible v5 release.

The transaction paths use the locally derived signature, report uncertain
broadcast outcomes without retrying, recheck inclusion at the blockhash expiry
boundary, and check blockhash freshness after passphrase entry. Stake listing
removes missing local hints only after a successful direct RPC lookup confirms
closure. Status now separates an unhealthy saved default from the selected
wallet, keystore KDF parameters are bounded before Argon2 runs, and the wrapper
sends Docker pull progress to stderr.

Validation after these changes: 78 unit tests passed across 19 files; TypeScript
lint/build and Prettier passed; Black, Python compilation, Node syntax, and
`git diff --check` passed; all 19 local Docker/Python E2E tests passed against a
freshly built Linux/amd64 image. The first Docker E2E run exposed a fixed mock
RPC fixture issue: it returned a hard-coded signature instead of the signature
embedded in the transaction. No live Devnet transaction ran. No system packages
were installed. The remediation is uncommitted and unpushed; checkpoint
`ac77a3a` remains the pushed documentation/specification state.
